## 1. Participant-first autonomy phase — locked authoring rule

Before each meaningful protagonist decision, CE/Story must first give materially present autonomous participants whose action/reaction window is due an opportunity to resolve their own intent.

Canonical ordering:

`committed scene state`
-> `eligible autonomous participants evaluated`
-> `participant intent selected from legitimate current state`
-> `owning resolver resolves participant action where required`
-> `committed participant consequence updates scene state`
-> `protagonist choice set derived from the updated state`
-> `player chooses protagonist intent`

Canonical shorthand:

> **Participants act before the player chooses what happens next.**

This does **not** mean every participant must visibly perform an action every beat. `hold`, `watch`, `wait`, `guard`, `refuse`, `do nothing`, or another legitimate non-action may be the participant's autonomous result.

The rule means the participant gets an autonomy opportunity before the protagonist's next decision whenever that participant is materially present and their action window is due.

---

## 2. No scripted participant obedience

Writing may define:
- the scene state;
- authored invariants;
- participant presence;
- legitimate objectives/stakes;
- hard Story requirements where intentionally fixed;
- observer-safe presentation.

Writing must not default to scripting an autonomous participant's exact tactical action merely because one outcome is convenient.

Participant intent must be derived from legitimate state such as:
- Knowledge and uncertainty;
- personality/current Disposition;
- relationships and Shared History;
- role/obligations;
- current objective and danger;
- capability/access;
- position and perceivable opportunities;
- prior committed actions;
- current world/Battle state.

Player choice != participant command.

Participant autonomy != random action.

Randomness may select only among already legitimate autonomous possibilities where the owning authority permits it; it may not manufacture motive, Knowledge, capability or history.

---

## 3. Player agency protection

Participant-first ordering must not collapse into NPCs playing the protagonist's game for them.

Preserve:
- autonomous participants may change the situation before the player chooses;
- autonomous participants may create, remove, alter or complicate protagonist affordances;
- autonomous participants may pursue their own objective instead of the protagonist's objective;
- participant action does not choose the protagonist's intent;
- after participant consequences commit, the player receives the next legitimate protagonist decision from the new state.

The engine loop is therefore:

`participant autonomy -> changed situation -> player intent -> owning resolver -> consequences -> participant autonomy -> next player intent`

where appropriate to the scene.

## 4. Academy Kakashi — Take Him Down correction

Existing branch entry remains:

`GET CLOSER -> FAILURE -> STAY ON THE PACKAGE -> pursuit SUCCESS -> TAKE HIM DOWN`

Still locked:
- Kakashi chooses immediate physical control rather than negotiation;
- his opening intervention separates ANBU Marked Target from the package;
- the package becomes neutral/contested rather than remaining in ANBU Marked Target custody;
- Pakkun is materially present and may participate as an autonomous temporary Story/Battle participant under current authority;
- this route must remain materially distinct from `DEMAND THE PACKAGE`.

### Superseded hard-scripted detail

The earlier authority fixed Pakkun to remain between ANBU Marked Target and the neutral package and fixed defeat to `package recovered + target escapes`.

That exact Pakkun action is now **superseded as a scripted requirement**.

Writing no longer dictates:

`Pakkun must guard/recover the package`.

Instead, once the package becomes neutral, CE evaluates Pakkun's autonomous action from the actual committed state before the player's next actionable decision/turn where the runtime seam permits it.

Legitimate Pakkun possibilities may include, if supported by current state:
- recover/secure the package;
- guard the package;
- block ANBU Marked Target's route to it;
- support Kakashi directly;
- pressure the target from another angle;
- hold position;
- another context-legitimate action.

This list is illustrative, not a hard-coded action table.

### Example realisation — NOT scripted canon

A particularly strong legitimate realisation is:

> Kakashi engages ANBU Marked Target while Pakkun independently recognises the exposed mission objective and secures the package.

If CE resolves that action legitimately, the Battle continues with ANBU Marked Target now needing to defeat/escape Kakashi while the package is already secured by Pakkun/Kakashi's side.

That outcome is Chronicle Engine at work because the participant changed the tactical state before the protagonist's next decision; it is not authored obedience.

## 5. Outcome consequence correction

Because Pakkun's exact autonomous action is no longer scripted, `TAKE HIM DOWN` defeat may not universally assume package recovery merely from the choice label.

The durable authored distinction is now:

### Demand the Package
- package remains in ANBU Marked Target custody going into Battle;
- Kakashi first seeks voluntary surrender;
- refusal escalates to Battle.

### Take Him Down
- Kakashi skips negotiation;
- his opening intervention makes the package neutral/contested before the main Battle state;
- autonomous participant actions may then change package control before/during the encounter through legitimate CE/Battle resolution.

Exact final package custody after a `TAKE HIM DOWN` Battle defeat must consume the committed participant/Battle state rather than a Writing-scripted assumption.

Therefore the earlier universal rule:

`Take Him Down defeat = package recovered + target escapes`

is superseded.

Instead:

> **Take Him Down defeat = ANBU Marked Target defeats Kakashi; target custody is lost; package custody is whatever the committed autonomy/Battle state legitimately established.**

If Pakkun autonomously secured the package first, Kakashi's side may still retain the objective despite losing the fight.

If he did not, another legitimate package result may occur according to the committed state and owning resolver.

## 6. Runtime / persistence requirement

Runtime must preserve the semantic participant action and its consequence, not reroll it because presentation refreshes.

A participant-autonomy receipt should preserve at minimum:
- scene/decision context;
- actor identity;
- actor-relative Knowledge basis;
- eligible intent or action class;
- selected intent;
- owning resolver/result where applicable;
- committed state changes;
- provenance sufficient for save/load/replay diagnostics.

Presentation text is downstream and does not itself create the participant action.
