## 10. Recovered CE / Coordination doctrine already durable

The following are not new proposals; the Kakashi work repeatedly reinforced existing durable architecture and they must survive chat retirement.

### 10.1 Intent before outcome

A player action is first a committed intent. The factual outcome belongs to the explicit resolver/transition owner. Presentation labels do not self-resolve.

### 10.2 Eligibility is not factual outcome

An eligible action or possible outcome does not mean the corresponding occurrence happened. CE evaluates from committed facts, not availability.

### 10.3 Participant-first autonomy before protagonist menu

Durable authority:

`Documentation/Coordination/Participant First Story Autonomy Runtime Ordering and Battle Boundary Contract 2026-09-15.md`

commit:

`06566ee81fe7c7856fd513d0225e621273f4bfaa`

Canonical loop:

`committed Story state`
→ `drain due participant-autonomy windows through legitimate resolvers`
→ `commit participant results/provenance`
→ `derive protagonist choices`
→ `commit protagonist intent`
→ `owning resolver`
→ repeat.

No free NPC Battle action. An autonomous action is either consumed before Battle or through an authorized Battle seam, never twice.

### 10.4 Independent post-resolution participant classification

Defeating one or more Battle participants does not imply they share one custody/death/escape/control disposition. Participants must be classified independently from committed facts.

Examples from the Kakashi route are content-specific, but the reusable doctrine is generic:

`Battle defeated` != `dead` != `captured` != `controlled` != `escaped`.

### 10.5 Battle victory is not Story semantics

Battle owns Battle facts. Story/World/CE own downstream semantic interpretation through explicit authority.

Victory cannot silently infer:

- death;
- custody;
- package/object possession;
- mission/Origin success;
- reward entitlement;
- participant relationship history;
- terminal completion.

### 10.6 Chronicle Receipt is a projection

The end-of-Origin Chronicle/Receipt must read already committed intent, outcomes, identities, order, custody/pursuit, Knowledge, and rewards/history. It is not allowed to recommit or infer missing history.

### 10.7 Presentation is reconstructible projection, not authority

Scene Board/dialogue/labels may project current committed state. Stale presentation state must be cleared/rebuilt on legitimate beat/scene transitions; presentation state must never become a hidden history owner.

## 11. CE POTENTIAL — high-value generic patterns recovered from runtime work

These are candidates for CE / Coordination promotion. They are deliberately **not** declared CE authority by this audit.

### CE POTENTIAL A — Factual downstream projection adapter contract

The strongest new generic lesson is the shape of current `34800`.

A context-specific reward/development adapter should:

1. accept exact factual inputs from the owning Story/World/Battle continuation;
2. verify exact source/subject/context identity;
3. issue source-scoped idempotent receipts;
4. call the canonical Progression / Inventory / Reward mutation APIs;
5. never create a second parallel Progression, Inventory, reward, or history system;
6. separate eligibility from grant;
7. separate Battle outcome from terminal entitlement;
8. fail closed if the canonical owner API is absent or if source identity mismatches;
9. preserve save/load/idempotence without duplicating grants.

This is broader than Academy Kakashi and is a useful CE integration pattern for Missions, Story occurrences, examinations, investigations, relationship events, and other fact-driven progression.

Recommended CE question:

> Should CE define a generic **Factual Projection / Consequence Adapter** interface whose job is to translate committed occurrence facts into calls to existing subsystem owners while emitting idempotent provenance receipts?

The name and exact API are open. The ownership principle is the candidate.

### CE POTENTIAL B — Caller continuation as an explicit capability

The caller-return bug exposed a reusable cross-system requirement.

When Story/Mission/World launches a subordinate runtime such as Battle, the subordinate runtime must preserve an explicit caller continuation capability/context through:

`launch -> interaction -> result -> claim/acknowledgement -> authored resume`.

A generic fallback destination must not silently consume or replace a valid caller continuation. If the authored resume cannot be performed safely, fail closed at the result boundary rather than pretending the caller no longer exists.

Recommended CE/Coordination question:

> Should subordinate-runtime transitions carry a stable, provenance-bearing continuation token/capability that is validated and consumed exactly once?

This would generalize beyond Battle to Exams, minigames, encounters, modal investigations, Arena subflows, and future Chronicle interactions.

### CE POTENTIAL C — Prepared vs released runtime capability state

The secure-package tranche revealed an important state distinction:

- code can be implemented/prepared;
- authority can still require the route to remain unreachable/fail-closed;
- production delivery/cache generation should advance only when the complete semantic release gate is satisfied.

This avoids exposing half-connected authority merely because source files exist.

Recommended Coordination/CE distinction:

`designed -> durable -> implemented/prepared -> source validated -> production released -> browser validated -> Golden`.

This may deserve an explicit **prepared-but-not-released** capability state in future runtime handoff doctrine.

### CE POTENTIAL D — Source-scoped idempotence as consequence provenance

`34800` uses source/route/kind/subject identity rather than global “already rewarded” booleans. This pattern is worth generalizing.

A consequence should be idempotent against the exact source fact that entitled it, not merely against a broad UI state or completion flag.

This strengthens:

- save/load;
- retry safety;
- repeated projection;
- partial grant recovery;
- auditability;
- future migration.

### CE POTENTIAL E — Occurrence-scoped transient state must survive reprojection

The Substitution Jutsu replacement is Combat-specific, but it exposes a cross-runtime state principle:

- unresolved transient state belongs to the live occurrence, not the DOM/render instance;
- rerender/reopen must not reset once-per-occurrence availability;
- save/load must preserve unresolved state deterministically;
- previously committed historical actions are immutable and must not be retroactively reinterpreted after a rules/palette supersession.

This principle may belong in a shared occurrence-state/save-load contract rather than CE itself.

### CE POTENTIAL F — Mixed-generation runtime is an authority hazard

The Kakashi loader family uses distributed parent/child cache generations. A cached parent can therefore request a different semantic generation than current source expects.

For Alpha, do not broad-redesign the boot architecture while closing #188.

Post-Alpha / bounded cleanup candidate:

- one manifest/build generation for a tightly coupled runtime family;
- or an explicit compatibility assertion that rejects mixed semantic generations.

This is infrastructure/coordination potential more than CE gameplay semantics, but it materially protects authority delivery.
