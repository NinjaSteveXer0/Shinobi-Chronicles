# Shinobi Chronicles — Whole-Build Competitive Synergy and PvP Audit Doctrine

**Date:** 2026-09-12  
**Owner:** Combat / Skills / Items / Weapons  
**Status:** **BINDING COMPETITIVE DESIGN / AUDIT DOCTRINE — EXISTING CONTENT MUST BE RE-EVALUATED BEFORE COMPETITIVE FREEZE**

## 1. Player decision

Stephen explicitly requires Bloodline PvP counterplay to be evaluated together with the rest of the complete Combat build.

Competitive balance is therefore not authored or audited at the level of one Bloodline, one Skill, one weapon, one Summon or one Character in isolation.

Canonical competitive object:

`Character representation + Stats/PL + prepared Skills + Bloodline/lineage state + weapon + gear + Summon + consumables + Fūin/attachments + Provenance + transformation/Hosted Entity state + relationship/cooperative capability + teammates + deployment/action economy + factual battlefield context`

The assembled package and the assembled team are the unit of competitive analysis.

---

## 2. No grandfathering by isolated balance

Previously-authored Skills, Equipment, weapons, gear, Summon enhancements, transformations, Bloodline effects, Conditions or other Combat packages remain current authority until explicitly superseded, but none are automatically considered competitive-ready merely because their individual numbers were previously accepted.

Before PvP/competitive freeze, relevant content must be revisited against realistic combinations.

Preserve:

**individually reasonable != safe in combination**  
**low numeric bonus != low strategic impact**  
**high rarity != permission to bypass counterplay**  
**old closure != competitive audit complete**

A package may require no changes after audit. The audit itself is still required.

---

## 3. Required build surfaces

Competitive review must account for every mechanically relevant surface that can alter Battle decisions or outcomes, including at minimum:

1. **Character representation / Base package**
   - Stats;
   - Base PL;
   - representation-specific capability facts;
   - legitimate Rank/identity facts only where mechanically consumed.

2. **Prepared Skills / repertoire**
   - direct output;
   - setup;
   - control;
   - defence;
   - mobility;
   - recovery;
   - contextual/hybrid effects;
   - action costs and opportunity costs.

3. **Bloodlines / dōjutsu / Kekkei Genkai / Kekkei Tōta / lineage capabilities**
   - possession;
   - Access;
   - stage/state;
   - exact expressions;
   - matchup interactions;
   - PvP counterplay.

4. **Weapons**
   - Effective Stat projection;
   - proficiency;
   - weapon-specific actions/riders;
   - range/handling;
   - material interaction;
   - source-owned special effects;
   - Provenance/synergy/compatibility.

5. **Gear / Equipment**
   - defence/mitigation;
   - sensory/utility;
   - movement/positioning;
   - resistance or condition interaction;
   - equipment slot opportunity cost;
   - source-specific restrictions.

6. **Summons**
   - Stat modifiers;
   - resolver-only effects;
   - elemental/affinity interaction;
   - action economy;
   - Summon-specific repertoire;
   - controller dependency;
   - deployment/targetability where separately authored;
   - relationship/contract/cooperation state where relevant.

7. **Consumables / pouch**
   - recovery;
   - cleanse;
   - temporary setup;
   - quantity scarcity;
   - action cost;
   - pre-Battle preparation constraints.

8. **Fūin / attachments / crafted modifications**
   - exact host object;
   - source-owned effects;
   - access/competence requirements;
   - stacking/supersession;
   - removal/counterplay;
   - provenance lineage.

9. **Transformations / Hosted Entities / Curse or transformation packages**
   - state transition cost;
   - cooperation/control;
   - Effective/Battle-state projection;
   - action economy;
   - loss-of-control risk;
   - source-owned Skills;
   - interaction with Bloodlines, Equipment and team effects.

10. **Conditions / transient markers / battlefield states**
    - duration;
    - stacking;
    - cleanse/suppression;
    - setup and payoff;
    - readability;
    - team interaction.

11. **Relationships / cooperative techniques / fusion packages**
    - exact participant requirements;
    - action sharing;
    - deployment cost;
    - failure/separation risk;
    - pair-specific development;
    - Hosted Entity interaction where relevant.

12. **Team composition**
    - role overlap;
    - role coverage;
    - setup/payoff chains;
    - target protection;
    - focus-fire capability;
    - control chains;
    - action-economy compression;
    - team-wide weaknesses and counters.

13. **Battlefield / terrain / information context**
    - line of sight;
    - range;
    - material;
    - environmental compatibility;
    - prepared terrain;
    - sensory information;
    - observer Knowledge;
    - escape/reposition routes.

This list is not exhaustive. Any future Combat-affecting system joins the audit surface automatically.

## 4. Provenance is a first-class build variable

Current project authority already preserves:

**provenance != free power**

and issue #116 remains open for exact created-instance / Crafting / Fūin Craft / Provenance Weapon semantics.

This doctrine adds the competitive requirement:

> **Where an exact weapon/item/creation has authored provenance-dependent synergy, compatibility, history or developed effects, that provenance must be included in whole-build evaluation.**

Provenance may materially affect competitive strength through exact authored routes such as:

- creator/wielder compatibility;
- long-term use history;
- legitimate developed technique access;
- attached seals/modification lineage;
- material provenance;
- named historical occurrence;
- relationship to a clan, institution, owner or Hosted Entity;
- specialised response to a particular Skill family or capability;
- inherited/customised handling knowledge;
- other exact source-owned expressions.

But provenance does **not** automatically mean:

- `old weapon = stronger`;
- `famous weapon = stronger`;
- `more history entries = more Stats`;
- additive Base PL;
- automatic Mastery;
- universal bonus stacking;
- random reroll power.

Competitive strength must come from the exact authored provenance interaction.

---

## 5. Build synergy is intentional

Shinobi Chronicles should allow players to construct genuinely powerful competitive builds.

The balancing target is **not** that every combination feels equally strong.

The target is:

- strong synergies are discoverable and rewarding;
- specialist builds can become frightening in their intended niche;
- team composition matters;
- provenance/history can create distinctive build identity;
- prepared Skills matter;
- Equipment choice matters;
- Summon choice matters;
- Bloodline choice matters;
- opportunity cost matters;
- counterplay remains available;
- no one package becomes universally mandatory.

A high-performing build should feel assembled, earned and strategically coherent rather than accidentally overpowered by one isolated multiplier.

---

## 6. Competitive audit must measure more than damage

Do not balance whole builds by one scalar DPS/PL score.

At minimum review the following strategic dimensions separately:

- **burst output**;
- **sustained output**;
- **mitigation / survivability**;
- **recovery / cleanse**;
- **control / denial**;
- **mobility / positioning**;
- **range / threat projection**;
- **information / sensing / concealment**;
- **setup requirement**;
- **action-economy efficiency**;
- **resource efficiency**;
- **reliability / consistency**;
- **flexibility across matchups**;
- **team enablement**;
- **team dependence**;
- **counter vulnerability**;
- **punish windows**;
- **scaling ceiling**;
- **Provenance-dependent payoff** where relevant.

An internal balancing worksheet/simulation may derive comparison metrics from these dimensions, but such an audit metric is not a new runtime PL system and must not replace existing Base / Effective / Battle PL semantics.

---

## 7. Stacking and double-count audit

Every competitive build review must identify whether two or more systems are rewarding the same underlying fact twice.

Examples to inspect:

- Bloodline Stat modifier + Skill multiplier + Summon affinity bonus all amplifying the same attack family;
- Equipment Stat bonus + provenance bonus both claiming the same mastery/history;
- transformation projection + Hosted Entity projection duplicating one source;
- Skill rider + gear passive both applying the same condition without intended stacking semantics;
- weapon proficiency + Bloodline Bukijutsu enhancement creating runaway multiplicative scaling;
- team aura + Summon enhancement + gear enhancement creating hidden global amplification;
- defensive resistance stacking that creates practical immunity;
- action refunds/assists/fusion creating more effective actions than the authored economy intends.

Preserve the existing source-owned modifier principle.

A source may be strong. The same source must not be counted several times through different labels unless the stacking is explicitly intended and competitively audited.

---

## 8. Competitive build anti-patterns

Redesign or constrain a package if whole-build testing shows any of the following:

- one Bloodline/weapon/Summon/gear piece is optimal for nearly every serious build;
- one provenance route universally dominates unprovenanced alternatives regardless of style;
- one stat or damage family scales several independent systems multiplicatively without sufficient cost;
- one team composition reliably wins before meaningful opposing decisions occur;
- one control chain creates effective permanent denial;
- one sustain package creates practical immortality;
- one defensive stack invalidates an entire discipline;
- one item/weapon requires another exact rare item merely to have counterplay;
- one Summon becomes mandatory because its passive value is universally useful;
- one synergy has no meaningful opportunity cost;
- one build remains top-tier across nearly every terrain, range and opponent type;
- rare provenance functions as unavoidable vertical power rather than distinct build identity.

---

## 9. Counterplay-first applies to the assembled package

The existing Bloodline PvP Counterplay-First doctrine is extended to whole builds.

For each representative competitive build ask:

> **What does the opposing player/team identify, disrupt, avoid, pressure, bait, exhaust, isolate or counter?**

Counterplay may target a dependency rather than the headline power.

Examples:

- deny the weapon user the range where provenance technique is strongest;
- separate the Summon-enhanced controller from the target it enables;
- force the Bloodline user to spend setup before their gear synergy comes online;
- destroy/dispel/sever an exact created object or attachment where authored;
- pressure the support Character sustaining the team engine;
- force an expensive transformation before the decisive exchange;
- exploit a team composition's weak cleanse, poor range, low mobility or lack of sensing;
- attack action economy rather than raw Stats.

This is preferable to universal hard-counter tables.

## 10. Representative-build testing

Before competitive freeze, Combat should maintain a set of representative build archetypes and adversarial matchup tests.

Examples of useful archetypes include:

- high-Ninjutsu elemental artillery;
- Bukijutsu/provenance weapon specialist;
- Bloodline control specialist;
- Genjutsu/information denial;
- high-Stamina defensive anchor;
- fast pressure/assassination;
- Summon-supported controller;
- transformation/Hosted Entity carry;
- Fūin/anti-capability specialist;
- sustain/recovery composition;
- multi-character fusion/cooperative build;
- balanced generalist team.

The purpose is not to force a fixed class system. These are test harnesses for finding degenerate interactions.

Every high-performing archetype should be tested against:

- a neutral/generalist opponent;
- at least one soft counter;
- at least one structurally unfavourable matchup;
- a team with comparable investment but different strategy;
- team-PvP action-economy pressure;
- terrain/context that helps it;
- terrain/context that hurts it.

## 12. Workflow for revisiting existing content

Do not perform an uncontrolled rewrite of every catalogue row at once.

Use a staged audit:

### Stage A — inventory
Create an authoritative list of mechanically active competitive surfaces and mark each:

- current authority;
- implemented?;
- runtime validated?;
- competitive-audited?;
- provenance-sensitive?;
- known stacking dependencies;
- known counterplay dependencies.

### Stage B — interaction map
Map major amplification and dependency edges, for example:

`Bloodline -> elemental Skill`  
`weapon -> Bukijutsu Skill`  
`Summon -> affinity / Stat`  
`gear -> mitigation`  
`provenance -> exact weapon expression`  
`Hosted Entity -> transformation package`  
`team support -> setup/payoff`

### Stage C — representative builds
Assemble plausible strong builds deliberately rather than waiting for players to discover every exploit first.

### Stage D — adversarial tests
Test those builds against counter-strategies, not only target dummies.

### Stage E — tune the smallest owning source
If an interaction is broken, adjust the narrowest correct source instead of globally nerfing unrelated systems.

### Stage F — runtime / Golden validation
Coding owns implementation and regression proof after mechanics are closed.

Design closure does not equal runtime balance validation.

---

## 13. No anti-fun flattening

Competitive balance must not produce a roster where every weapon, Bloodline, Summon and Skill is numerically interchangeable.

Desired state:

> **Players should be able to discover brutal combinations, but brutal combinations should have requirements, opportunity costs, exposure and counterplay.**

A specialised team may dominate the matchup it was built to exploit and struggle badly elsewhere.

That is strategic diversity, not imbalance by itself.

The failure state is a build that dominates most matchups with little meaningful sacrifice or counterplay.
