# Shinobi Chronicles — Autonomous Alpha Specialist Execution Mode

**Date:** 2026-09-13  
**Owner:** CE / Codex / Coordination  
**Status:** **BINDING PROJECT-WIDE ALPHA OPERATING MODE**

---

## 1. Purpose

Shinobi Chronicles is now far enough through Alpha closure that Stephen should no longer act as the routine production dispatcher, message bus, or micro-manager between specialist workspaces.

The project therefore enters **Autonomous Alpha Specialist Execution Mode**.

The intended operating model is:

- **Stephen** = executive / approver / final taste and priority authority;
- **CE / Codex / Coordination** = central coordination hub, semantic firewall, traffic controller, cross-system reconciliation owner;
- **specialist workspaces** = autonomous executors inside their durable ownership boundaries;
- **GitHub source/documents/issues** = durable production authority, inbox/outbox, handoff transport and evidence ledger.

Canonical shorthand:

> **Stephen sets direction. CE coordinates. Specialists execute. GitHub carries the work.**

and:

> **Independent execution does not mean independent game design.**

---

## 2. Primary priority

**Finish Shinobi Chronicles Alpha.**

Autonomy exists to reduce coordination drag and Stephen micro-production, not to widen scope.

Do not turn post-Alpha ideas into Alpha blockers.

Do not reopen closed architecture without genuinely new evidence, a real contradiction, or an Alpha blocker.

---

## 3. Authority order

For production-critical claims and work:

1. current GitHub source;
2. durable SC / CE documents and commits;
3. current closed specialist authority;
4. Project memory;
5. inference.

Always preserve:

**discussion != design closed != durable authority != implemented != runtime validated != Golden/regression GREEN**

A specialist must not claim a later stage merely because an earlier stage is complete.

---

## 4. Default specialist behaviour

A specialist should no longer wait for Stephen to restate work that is already durably routed or clearly within its ownership.

At the start of a work cycle, the specialist should:

1. inspect current GitHub authority relevant to its owner domain;
2. search open GitHub issues targeted to its owner token;
3. identify the highest-priority legitimate owned task that is currently actionable;
4. consume upstream durable contracts before acting;
5. execute the work autonomously inside its ownership boundary;
6. preserve any production-relevant result durably;
7. comment exact evidence on the source issue;
8. close the issue when genuinely complete;
9. create the next downstream GitHub handoff itself only when another owner truly must act.

Do not ask Stephen to copy packets between chats when GitHub issue tooling is available.

Do not wait for Stephen to say `continue` when the next owned action is already unambiguous and authorised.

---

## 5. What specialists MAY do autonomously

Without Stephen manually prompting each step, specialists may:

- implement a closed contract they own;
- author content already requested and bounded by durable authority;
- perform runtime/source/browser validation already routed to them;
- reconcile current source against a durable owner contract;
- continue from a durable checkpoint;
- fix confirmed implementation drift inside their ownership;
- perform required archaeology before archive/retirement;
- consume incoming GitHub handoffs;
- create durable documentation for closed owner decisions;
- create downstream GitHub issues when a real dependency exists;
- close completed incoming issues with exact evidence;
- classify non-blocking future work as QUEUE rather than interrupting current Alpha work;
- record useful reinforcement without creating unnecessary traffic.

The specialist should prefer completing work over asking Stephen to restate known requirements.

---

## 6. What specialists MUST NOT do autonomously

Autonomy is **execution authority**, not permission to redesign the project.

A specialist must not, without explicit authority:

- invent a new major system;
- materially widen Alpha scope;
- rewrite closed Story/canon because another version seems preferable;
- alter another owner's semantics merely to simplify implementation;
- invent missing Registry identity, Rank, ownership, progression, capability or Knowledge truth;
- silently resolve a cross-system contradiction in its own favour;
- convert a QUEUE idea into a current Alpha blocker without new evidence;
- replace approved visual/narrative/content authority because it prefers another direction;
- collapse specialist boundaries;
- fabricate implementation or Golden status;
- use Stephen as routine transport.

Preserve specialist non-collapse rules, including:

PL != Progression  
Rank != Progression  
Acquisition != Progression  
Registry identity != ownership  
ownership != assignment != deployment  
Promotion != roster-transition completion  
Battle victory != Promotion  
mission completion != automatic Progression  
Knowledge != Access != Competence != Power != Mastery  
World Truth != observer Knowledge != presentation  
location != event != opportunity

## 7. When to escalate to CE / Codex / Coordination

CE is the default escalation point for cross-system uncertainty.

Escalate when there is:

1. a genuine authority contradiction;
2. unclear ownership between specialist domains;
3. a cross-system collision;
4. stale/superseded authority that cannot be reconciled locally;
5. a proposed exception to reusable doctrine;
6. a new reusable Chronicle Engine semantic requirement;
7. a dependency involving several owners;
8. uncertainty whether a discovered issue is Alpha-critical or merely queued;
9. a need to reconcile Story, World, Registry, Progression, Combat, Acquisition or Coding truth;
10. a decision whose effect would materially alter more than the specialist's own surface.

When escalating, provide exact evidence and the smallest real decision needed.

Do not send CE a dump of everything discussed.

A good escalation removes uncertainty.

## 8. When Stephen must be asked

Stephen should now be interrupted only when his judgement is genuinely required.

Examples:

- two or more legitimate creative directions require owner taste;
- a major product-priority trade-off is unresolved;
- Alpha scope would materially change;
- a closed design would need reopening for a reason not already authorised;
- visual/narrative preference cannot be decided from durable authority;
- irreversible/high-cost work depends on a subjective choice;
- a new game-level premise needs approval;
- Stephen's explicit image-generation authorisation is required.

Do not ask Stephen questions whose answers are already present in GitHub authority.

Do not ask for permission to perform clearly routed owned work.

## 11. Priority and traffic rules

### SEND NOW

Use only when another owner must act before current Alpha work can proceed or the current executable lane is blocked.

### QUEUE

Use for real future work that does not block the current task.

Do not interrupt an active Alpha blocker merely because a queued issue exists.

### RECORD ONLY

Use for reinforcement, useful durable information, or already-closed facts requiring no current owner action.

Repeated already-closed information should normally be:

**REINFORCEMENT / VALIDATION — NO NEW ACTION.**

At most one cross-workspace coordination packet should emerge from one substantial unit of specialist work.

If several owners may be involved, route one consolidated issue to CE / Codex / Coordination unless exactly one direct recipient is obvious and immediate.

## 15. Coding and implementation discipline

Coding should autonomously consume exact closed contracts and implement them without asking upstream owners to restate semantics.

Coding must not become lore/design authority when a contract is missing.

If implementation exposes a genuine semantic contradiction or missing owner decision:

- preserve the exact failing evidence;
- route only that contradiction;
- continue unrelated executable work where possible.

Do not turn one blocked row into a project-wide stop unless it actually blocks the current Alpha path.

---

## 16. Durable-result rule

Production-relevant specialist decisions must become durable without Stephen having to say `save this`.

Preserve when:

- approval/closure occurred;
- Story/canon changed;
- a future gameplay/capability result changed;
- an exception was created;
- a named mechanic/route/content contract was closed;
- an exact ID/formula/path matters;
- another owner will depend on it;
- losing it would force reconstruction;
- substantial design effort already occurred.

If uncertain, preserve lightly with truthful status such as:

DISCUSSION / CANDIDATE / PROPOSAL / CLOSED / SUPERSEDED / PROTECTED GAP / POST-ALPHA.

Durability != approval != implementation != runtime validation != Golden.

## 17. Completion evidence

When a specialist finishes routed work, its GitHub closure should identify the smallest sufficient evidence, such as:

- exact document/source path;
- commit SHA;
- implementation commit;
- test/runtime/browser result;
- remaining known gaps;
- downstream issue number if one is genuinely required.

Do not close an issue merely because work was discussed.

Do not leave completed work open waiting for Stephen to acknowledge it.

If no actionable owned issue exists, the specialist should report that state briefly and avoid inventing work merely to stay busy.
