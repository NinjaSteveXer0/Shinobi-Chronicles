## 2. Canonical validation ladder

For every production surface, keep these states separate:

1. **DISCUSSION / PROPOSAL** — idea or candidate rule only.
2. **DESIGN CLOSED** — owning specialist has closed semantics/content.
3. **DURABLE AUTHORITY** — closed contract is recorded in current durable source/docs.
4. **IMPLEMENTED** — production source contains the required behaviour/data.
5. **SOURCE / UNIT / HEADLESS VALIDATED** — deterministic non-browser execution proves the tested source behaviour.
6. **INTEGRATION VALIDATED** — interacting runtime modules prove the seam/round-trip under executable conditions.
7. **INSTALLED-BROWSER VALIDATED** — the actual production browser/load path proves the player-facing behaviour.
8. **GOLDEN / REGRESSION GREEN** — the required end-to-end production path passes against the exact source frontier and no unresolved blocker remains for that Golden scope.

Never promote a surface to a later state merely because an earlier state is GREEN.

Canonical shorthand:

> **design closed != implemented != source/headless validated != installed-browser validated != Golden/regression GREEN**

## 3. Evidence rules

A validation claim must identify, where applicable:

- exact commit/source frontier;
- exact runtime/module/load path exercised;
- exact test/harness or browser path used;
- exact save state/fresh-save conditions where relevant;
- exact PASS/FAIL result;
- any known untested boundary;
- issue/authority scope the evidence closes.

Old PASS evidence remains useful only while the tested surface and its causal dependencies remain materially unchanged.

A source change that affects the tested behaviour invalidates inherited GREEN for that surface until the relevant test is rerun.

## 4. Golden definition

A **Golden** is not a document review, source inspection, existence check, unit test, static diagnostic, or headless-only pass.

For Shinobi Chronicles Alpha, Golden requires the actual production/browser-facing path with real production source/load order and authoritative assets/mappings.

A Golden claim must prove the relevant player-facing loop, persistence, return seams and non-leak boundaries in the installed/production browser environment.

If an environment cannot execute the installed browser path, it may produce source/headless evidence only and must leave Golden unclaimed.

## 7. Save/load and idempotence doctrine

For any semantic state expected to persist, browser/Golden validation must test the relevant save/reload boundary.

UI refresh, panel reopen, map reopen, hover/focus, route redraw or re-render must not:

- reroll a committed occurrence;
- duplicate a reward;
- duplicate teammate acquisition;
- duplicate Promotion;
- mutate Knowledge merely by presentation;
- respawn resolved one-shot content;
- erase legitimate reservation/custody/history;
- recompute a committed factual choice into a different result.

Committed factual history is replayed/reconstructed, not rerolled.

## 8. Zero-leak doctrine

Hidden/unknown information must not leak through any presentation surface, including where relevant:

- visible text;
- tooltip;
- DOM content;
- dataset/attribute;
- accessible name/description;
- focus order;
- pointer target/cursor/hitbox;
- URL/navigation metadata;
- hidden counters/denominators.

World Truth != observer Knowledge != presentation.

A browser surface that visually hides a secret but leaks it through DOM/accessibility metadata is NOT Golden GREEN.

## 9. Failure and defect handling

When validation fails:

1. record the exact failing path/state;
2. determine whether the defect is implementation, stale authority, missing owner content, asset/mapping, persistence, or validation-environment related;
3. fix only within current owner authority;
4. route one exact upstream/downstream dependency if another owner must act;
5. rerun the affected gate;
6. do not reopen unrelated closed architecture.

A failure in one browser lane does not automatically invalidate unrelated source/headless GREEN, but it blocks Golden for the affected Golden scope.
