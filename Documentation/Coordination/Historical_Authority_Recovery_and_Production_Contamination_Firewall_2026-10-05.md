## 1. Incident that activated this firewall

During the 2026-10-05 forgotten-UI / conformance recovery work, current production correctly gained stronger conformance tooling but also reintroduced stale presentation content:

- `UI/my_clan_browse.png` / `UI/my_clan_inspection.png` were rebound as literal My Clan stage backgrounds even though Stephen no longer wanted those backdrops in the current My Clan presentation;
- `UI/practical.png` / `UI/exams.png` were rebound literally as activity-screen backgrounds, visually reintroducing baked Kage Naruto / Jōnin Sasuke fixture content onto ordinary player surfaces;
- this conflicted with the current Real-Player-First rule that Stephen's ordinary browser surfaces consume his real protagonist/current team rather than broad synthetic fixture rosters.

This is not evidence that GitHub itself is corrupt. It is an **authority contamination / resurrection failure**:

> historical or previously approved material was treated as a current literal production obligation without first proving that its embedded presentation content was still compatible with newer authority.

The project must protect against this failure class as strongly as it protects against duplicate runtime owners.

## 2. Core law

> **Historical existence is not current production authority.**

> **Recovery is read-only until explicitly re-ratified against current authority.**

> **A surviving asset/document/module may be evidence that a design existed; it may not become production-active merely because archaeology rediscovered it.**

And:

> **Never restore a historical container when only the underlying design principle survived.**

Examples:
- recover Chronicle Interaction depth semantics without restoring an obsolete literal `convo.png` shell;
- recover My Clan Browse / Inspection behavior without forcing an unwanted old backdrop;
- recover Exams / Practical composition ideas without projecting baked synthetic Characters over real-player state;
- recover old animation quality without restoring retired patch-era runtime ownership.

---

## 3. Mandatory recovery classification

Before any historical asset, module, document, UI master, Story package, fixture, or queue item changes production, classify it as exactly one:

### CURRENT AUTHORITY — SAFE TO CONSUME
Current durable authority still explicitly requires the exact thing being restored.

### CURRENT PRINCIPLE / HISTORICAL CONTAINER
The underlying behavior/design survives, but the old asset/module/container is not itself production authority.

Default action: consume the principle; do not restore the old container literally.

### HISTORICAL EVIDENCE — OWNER RE-RATIFICATION REQUIRED
Potentially useful recovered material whose current status is unclear.

Default action: no production mutation.

### SUPERSEDED / RETIRED
Must not be reintroduced.

### FIXTURE / TEST-ONLY
May exist in QA/dev paths but must not leak into ordinary player surfaces.

### CURRENT OWNER REJECTED / NO LONGER NEEDED
Must be removed from active consumption even if an older document called it ACTIVE.

---

## 4. Asset resurrection gate

Before a visual master can be classified or restored as **ACTIVE PRODUCTION MASTER**, all of the following must be true:

1. current owner still wants literal runtime consumption;
2. current durable UI authority explicitly supports literal use;
3. the asset contains no stale dynamic/player-specific truth that can contradict runtime state;
4. the asset contains no synthetic fixture identities presented as current player truth;
5. no newer code-first presentation has superseded the need for the literal bitmap;
6. browser proof demonstrates that literal consumption improves or preserves the accepted current presentation;
7. watched-path and regression coverage exist.

If any item fails, default to:

> **REFERENCE / COMPOSITION MASTER**

not ACTIVE.

Physical presence in `UI/` is never sufficient.

## 5. Baked dynamic-state contamination rule

A raster/concept containing any of the following is presumptively **not safe for literal ACTIVE consumption** unless current authority explicitly makes those values decorative-only and browser-safe:

- Character identity;
- current team;
- current Rank;
- Stats / PL;
- Ryō;
- reputation;
- mission counts;
- assignments;
- village/world status;
- current objective;
- dynamic announcements;
- discovered rumours;
- route availability;
- current rewards;
- owned/equipped state;
- synthetic fixture roster members.

Such masters are normally composition/reference blueprints whose dynamic content must be rebuilt from code/data.

Canonical:

> **dynamic truth must live in runtime authority, not in recovered pixels.**

## 6. Real-player contamination gate

Ordinary player surfaces must never gain synthetic/dev/fixture Characters merely because a historical UI master displayed them.

Current Alpha rule remains:

> **real player state first; dev fixtures remain explicit dev/test overrides only.**

Required negative assertions for affected surfaces should prove where practical:

- Exams participants == exact legitimate current-team/current-caller participants;
- Practical participants == exact legitimate current-team/current-caller participants;
- My Clan roster/formation == actual ownership/assignment state;
- no literal historical bitmap injects Kage Naruto, Jōnin Sasuke, or another fixture identity into those ordinary surfaces;
- test fixtures may still exist in dedicated QA/dev modes without contaminating production presentation.

Do not globally ban those Character IDs; they are legitimate elsewhere. Ban **unauthorised projection into the wrong surface/context**.

## 7. Supersession-before-resurrection check

Before restoring historical material, compare it against:

1. current live GitHub source;
2. current durable contracts;
3. newer owner decisions;
4. current runtime responsibility owner;
5. current browser-accepted presentation.

The recovery task must state:

```text
what survived?
what was superseded?
what exact historical container is being considered?
why is literal restoration required, if at all?
what newer authority could it contaminate?
```

A recovery PR without this comparison fails closed.

---

## 8. No archaeology-driven mutation by default

Archaeology/recovery tools and audits are observers by default.

They may:
- discover old authority;
- classify drift;
- surface activation gates;
- recommend re-ratification;
- create a bounded handoff.

They may not automatically:
- re-enable old modules;
- re-add removed UI masters;
- restore old assets to production CSS;
- repopulate runtime rosters from historical fixtures;
- reopen retired state writers;
- change Story content;
- promote an old queue item directly into runtime.

Canonical:

> **detect -> classify -> re-ratify -> implement**

not:

> **detect -> restore**

---

## 9. Production conformance must detect contamination, not merely missing consumption

The conformance system must check both directions:

### Missing-consumer failure
Current authority expects a consumer, but none exists.

### Contamination failure
A consumer exists because stale/historical/superseded material has been reintroduced where current authority does not require it.

Therefore `OBSERVED` is not automatically good.

A surface can be:

> **OBSERVED BUT WRONG**

if the wrong historical asset/content is visibly present.

Conformance must validate **correct current authority**, not maximum visible asset consumption.

## 11. PR contamination checklist

Any recovery/conformance/legacy-restoration PR touching current player surfaces must answer:

- Is this adding back something previously removed?
- Why was it removed or bypassed?
- Is the old thing still current authority?
- Does it contain baked dynamic/player-specific data?
- Does it introduce synthetic fixtures into normal play?
- Does it override a newer accepted code-first presentation?
- What negative assertion proves no stale content leaked?
- What exact current owner decision authorises literal restoration?

If the PR cannot answer these, it must not merge as a production restoration.

---

## 12. Protected baseline / rollback discipline

For substantial recovery or conformance changes:

- record exact pre-change `main` SHA;
- keep the recovery change in its own coherent branch/PR;
- do not mix archaeology restoration with unrelated gameplay work;
- keep a clean rollback point;
- compare changed player-facing files against the pre-change baseline;
- preserve all unrelated accepted behavior;
- require exact negative contamination tests before merge.

A conformance improvement is not permission to alter presentation simply to make an old asset 'observable'.

## 14. Final lock

> **The project must be protected from two opposite failures: forgetting current authority, and resurrecting superseded authority. Recovery systems exist to find truth, not to maximise old-content consumption. Historical assets and modules are evidence first; production authority only after explicit current re-ratification.**

> **A missing feature is a defect. A resurrected obsolete feature is also a defect.**
