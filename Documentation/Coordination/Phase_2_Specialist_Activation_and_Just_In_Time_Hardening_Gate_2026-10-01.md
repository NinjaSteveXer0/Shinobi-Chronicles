# Shinobi Chronicles — Phase 2 Specialist Activation + Just-in-Time Hardening Gate

**Date:** 2026-10-01
**Owner:** Stephen / CE / Codex / Coordination
**Status:** BINDING PHASE-2 PROCESS SAFEGUARD

## 1. Problem

Several specialist workspaces were authored at different stages of project maturity.

Phase 2 must not assume that an older specialist rule set automatically reflects the project's current standards for:

- Chronicle persistence;
- observer Knowledge;
- current-team truth;
- reward causality;
- idempotence;
- semantic ownership;
- browser acceptance;
- Golden freezes;
- CE interactions;
- player-readable presentation.

At the same time, Alpha must not be delayed by speculative rewrites of every specialist charter.

## 2. Rule

Before a specialist begins its first substantial Phase-2 implementation/content tranche, CE / Codex / Coordination performs one bounded **Activation Audit** of that specialist's current durable authority.

Result must be one of:

- **CURRENT — NO HARDENING REQUIRED**
- **CURRENT WITH BOUNDED ADDENDUM**
- **STALE / CONTRADICTORY — MUST RECONCILE BEFORE IMPLEMENTATION**

Do not rewrite rules merely because they are old.

Do not allow old rules to control production when current evidence proves them stale.

## 3. Minimum Activation Audit

Check:

1. owner boundary remains correct;
2. current terminology/non-collapse laws are preserved;
3. source fact vs derived state vs presentation is explicit;
4. persistent writes have stable identity/idempotence;
5. save/load implications are declared;
6. observer Knowledge/hidden-content boundary is explicit;
7. current-team / ownership / assignment distinctions are preserved where relevant;
8. rewards/resources have causal source rather than filler;
9. retries/failures cannot duplicate grants;
10. UI cannot fabricate semantic state;
11. CE may consume facts but cannot silently seize specialist authority;
12. RED/AMBER/GREEN/GOLDEN meanings are current;
13. Stephen's real-player browser acceptance remains final;
14. frozen Phase-1 Origins are not reopened incidentally;
15. post-Alpha ideas are not promoted into Alpha blockers.

## 4. Specialist-specific examples

### World / Missions / Events / Rewards
Require:
- Reward Spectrum Firewall;
- causal payer/source for Ryō;
- non-material reward spectrum;
- failure/partial-success preservation;
- no morality payout;
- no filler loot;
- no duplicate cash fragmentation.

### Progression / Development
Require:
- Character-specific persistent development;
- no direct PL grants;
- current-team/activity-participant separation;
- exact EXP/evidence ownership;
- visible ceilings;
- Skill-learning source separation.

### Combat / Skills / Items / Weapons
Require:
- mechanics separate from reward/progression ownership;
- exact target/effect semantics;
- Skill catalogue != Skill Access;
- Battle package != Story contextual capability;
- no hidden Battle-only assumption leaking into Story.

### Writing
Require:
- common-sense/causality gate;
- rational actor knowledge;
- no exposition invented to solve runtime problems;
- no generic personality flattening;
- no route/content rewrite of frozen Origins.

### UI / Assets
Require:
- presentation consumes state;
- no semantic reroll;
- no baked dynamic HUD data;
- visual representation != persistent Character identity;
- approved asset-only changes stay surgical.

### Character Creation / Visuals
Require:
- exact asset approval;
- no publication before approval;
- correct asset family/path;
- remote asset-vault workflow;
- no Stephen local Git/PowerShell.

### Acquisition / Character Systems
Require:
- candidate != ownership;
- ownership != assignment;
- purchase != current team;
- acquisition commits exact stable Character/object identity.

### PL / Registry / Rank
Require:
- PL derived from Stats;
- representation != formal Rank automatically;
- formal Promotion separate from Battle victory;
- stable identity survives visual/card changes.

## 5. No broad stop-the-world audit

This gate is **just in time**.

Example:

- Rewards becomes active -> audit Rewards now.
- Persistent Development becomes active -> audit Progression now.
- Character Shop becomes active -> audit Acquisition now.
- Elemental Training becomes active -> audit Combat/Progression now.

Do not suspend unrelated Alpha work to audit dormant systems.

## 6. Closure

The Activation Audit result should be recorded in the relevant GitHub issue/comment.

If no gap exists, record:

**REINFORCEMENT / VALIDATION — NO NEW ACTION**

If a gap exists, add the smallest durable correction required.

## 7. Final rule

> **Phase 2 does not trust age, volume or familiarity as proof that a specialist contract is current. It checks the live authority when that owner becomes active, hardens only real gaps, and then moves forward.**
